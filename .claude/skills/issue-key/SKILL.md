# /issue-key — 고객·라이선스 운영

## 이 스킬이 지키는 것

원장이 두 개다. **Cloudflare D1**(키·좌석, 서버가 자동 기록)과 **구글 시트**(거래·문의, 사람이 기록).
두 원장이 어긋나면 고객이 활성화를 못 하거나, 돈을 안 받고 키가 나간 것이다.
**모든 처리 끝에 양쪽을 대조한다.**

관리자 화면: `https://numdraw-activation.numdraw.workers.dev`
`/admin/issue`(발급) · `/admin/list`(조회) · `/admin/revoke`(정지) · `/admin/release`(좌석 반납)

## Phase 0 — 무슨 요청인지 판별

| 요청 | 절차 |
|---|---|
| 입금 확인함 / 키 발급 | A. 신규 발급 |
| PC 교체·재설치 | B. 좌석 반납 |
| 환불·부정사용 | C. 키 정지 |
| 사용법·오류 문의 | D. 문의 대응 |
| 상태 확인 | `/admin/list` 조회 + 시트 대조 후 보고 |

이전 이력이 있는 고객이면 **시트에서 과거 처리(반납·정지·문의)를 먼저 읽고** 시작한다.

## A. 신규 발급

1. 사람이 확인한 **입금 사실**을 입력으로 받는다. 에이전트가 입금을 판단하지 않는다.
2. 거래 대장에 행 추가 — `거래일 / 구매자 / 연락처 / 플랜 / 금액 / 입금확인일`
3. `/admin/issue` 발급 안내 → 발급된 키는 **마스킹으로만** 기록 (`ND2-JS9M3-****-****-0T3A9`)
4. 안내 메일 문안 작성 → **[승인]** → 사람이 발송 → `메일발송일` 기록
   - **첨부 필수**: `외관집계표_양식.xlsx` — 홈페이지가 유료 플랜 공통 혜택으로 약속한 물건이다.
     빠뜨리면 약속한 혜택이 전달되지 않는다
5. 며칠 뒤 `/admin/list` 로 활성화 확인 → `활성화 좌석수` 갱신.
   활성화가 없으면 설치에 막혔을 가능성 → 후속 안내 문안 제안

**메일 문안 규칙**
- 첫 줄에 결론(발급 완료). 인사말로 시작하지 않는다
- 활성화 방법 3줄 이내: 프로그램 실행 → 키 입력 → 활성화
- 2대까지 설치 가능, PC 교체 시 좌석 반납으로 처리한다는 안내 포함
- 체험판과의 차이(PDF 저장 제한·워터마크 해제) 한 줄
- 홈페이지에 없는 혜택을 메일에서 만들지 않는다

## B. 좌석 반납

1. 사유를 시트 비고에 기록
2. **[승인]** `/admin/release` 실행
3. "새 PC 에서 같은 키로 활성화하면 됩니다" 안내 문안
4. `/admin/list` 로 재활성화 확인

## C. 키 정지

되돌리기 어렵다. **사유와 근거를 시트에 먼저 남기고, 반드시 승인을 받는다.**

1. 시트에 사유·근거 기록 → 2. **[승인]** `/admin/revoke` → 3. 환불이면 처리일·금액 기록

## D. 문의 대응

1. 문의 대장에 접수 행 추가 (`접수일 / 채널 / 문의자 / 내용 / 분류`)
2. 답변 초안 — 기능 관련은 **코드나 `web/guide.html` 에서 확인한 사실만** 쓴다
3. **[승인]** → 사람이 발송 → `답변일` 기록
4. 같은 분류가 3건 넘게 쌓이면 `web/guide.html` FAQ 보강을 제안한다
   (문서를 고치면 그 문의는 더 오지 않는다)

## 대장 양식

**거래**: `거래일 / 구매자 / 연락처 / 플랜 / 금액 / 입금확인일 / 라이선스키(마스킹) / 발급일 / 메일발송일 / 활성화 좌석수 / 상태 / 비고`
**문의**: `접수일 / 채널 / 문의자 / 내용 / 분류 / 답변일 / 재발방지 조치`

상태: `정상` `정지` `환불` `베타` · 분류: `사용법` `오류` `구매` `환불` `기능요청`

시트가 아직 없으면 `.claude/skills/issue-key/assets/` 의 CSV 두 개를 구글 시트로 가져오게 안내한다.

## 실행

```
Agent(subagent_type: "license-desk", model: "opus",
      prompt: "<요청 유형 A~D>. 고객: <...>. 확인된 사실: <...>")
```

## 자주 나는 문제

| 증상 | 대응 |
|---|---|
| 관리자 화면 503 | `ADMIN_TOKEN` 미등록/24자 미만. 사용자가 별도 터미널에서 재등록 |
| 좌석 반납 500 | 1회 재시도 → 실패 시 `/admin/list` 상태를 보고, 고객에겐 "확인 중" 안내 |
| 시트와 D1 불일치 | 임의로 정하지 않는다. 양쪽 값을 나란히 보고하고 사람 판단 |
| 고객이 키 분실 | `/admin/list` 에서 구매자명으로 확인(마스킹), 전체 키는 사람이 직접 전달 |

## 테스트 시나리오

- **정상**: "홍길동 평생이용권 입금 확인했어" → 시트 행 → 발급 안내 → 메일 문안 → 승인 대기
- **에러**: 관리자 화면 503 → 발급 중단, 토큰 재등록 안내, 시트에는 "발급 대기" 로 남김

## 금칙

- 전체 키 문자열을 대화·파일에 남기지 않는다 (마스킹만)
- 고객 개인정보를 저장소에 커밋하지 않는다 (시트에만)
- 입금 여부를 추정해서 발급하지 않는다
- 메일을 대신 발송하지 않는다 — 문안까지가 범위
- `ADMIN_TOKEN`·개인키를 출력하거나 파일에 쓰지 않는다
